topic: NOFX absorption plan — what patterns from NoFxAiOS/nofx crypto-bot should adopt, adapt, or reject
updated: 2026-07-19T00:09
---

- (decision) Absorb NOFX patterns selectively — adopt provider abstraction, MCP client interface, encrypted credentials, runtime/LLM separation. Reject monolithic Go backend; crypto-bot stays Python+OpenClaw.
- (capability) CAP-1: MCP-style provider abstraction — unified AIClient interface with hot-swappable providers (OpenAI, DeepSeek, Claude, Gemini, Qwen), per-model rate limits, fallback chains
- (capability) CAP-2: Runtime/LLM decision separation — decision engine runs in dedicated process with position limits, order validation, risk guards independent of LLM context
- (capability) CAP-3: Encrypted credential store — AES-GCM encrypted local store for API keys, exchange secrets, wallet private keys, decrypted only in-memory per session
- (capability) CAP-4: Grid trading engine — configurable price-level grid with states (empty/pending/filled), auto-hedging, portfolio-aware position sizing
- (capability) CAP-5: Signal overlay system — process external signals (Vergex, TradingView webhook) into weighted trade suggestions consumed by active strategies
- (capability) CAP-6: Three-layer agent memory (chatHistory/TaskState/ExecutionState) — borrowed design principles for OpenClaw agent memory management, not full port
- (constraint) Must stay Python-based — crypto-bot ecosystem is Python; introducing Go runtime would split dev focus and complicate deployment
- (constraint) Must remain OpenClaw-native — NOFXi agent embedded in Go process; we use OpenClaw as agent runtime. Agent patterns from NOFX must adapt, not port.
- (constraint) x402 pay-per-call deferred — requires USDC wallet, Claw402 gateway integration, and Base L2 infrastructure. High complexity for uncertain gain over existing LLM proxy.
- (note) NOFX: 9 exchanges (Binance, Bybit, OKX, Hyperliquid, KuCoin, Gate, Aster, Lighter). crypto-bot currently 2 (Binance, Bybit). Exchange expansion is separate effort.
- (note) NOFX: 81 docs multi-idioma vs crypto-bot minimal docs. Documentation infrastructure is gap but not urgent.
- (decision) Prioritize CAP-1 (MCP provider abstraction) as first implementation — enables model diversity, fallback, cost optimization. Highest leverage for lowest implementation cost.
- (decision) CAP-2 (runtime separation) is second priority — security model where LLM cannot directly place orders. Requires architectural refactor of agent_desk.py and paper_engine.py.
- (decision) CAP-3 (encrypted credentials) is quick win — integrate python cryptography Fernet or similar into existing config_loader.py. Straightforward.
- (decision) CAP-4 (grid trading) is new strategy type — implement as strategy_registry plugin with its own state machine. Does not require new infrastructure.
- (decision) CAP-5 (signal overlay) can leverage existing event_bus.py — signals become event type consumed by strategy engine.
- (decision) CAP-6 (agent memory) adopt principles only — OpenClaw owns memory layer. Write guidance doc for memory hygiene (what lives in chatHistory vs TaskState vs ExecutionState).
